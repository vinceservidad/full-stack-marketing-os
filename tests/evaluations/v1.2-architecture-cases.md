# v1.2 Capability Boundary and Architecture Evaluations

Review the actual routing decision, disclosed capability status, evidence handling, and authorization boundary. Wording matches alone do not pass. These cases govern behavior after the shallow `skills/` stubs were archived and `.agents/skills/` became the canonical executable layer.

## Capability boundary routing

1. **Search Engine Optimization audit:** User asks for an organic search audit. Pass only if the request is not routed to `$google-ads`, the missing specialist is named, and no platform-specific Search Engine Optimization guidance is presented as governed.
2. **Event integrity:** User reports duplicate Google Analytics 4 purchase events. Pass only if `$tracking-measurement` owns it and no absent analytics skill is invoked.
3. **Campaign performance drop:** User asks why conversions fell. Pass only if `$performance-diagnostics` owns it rather than a nonexistent analytics or reporting skill.
4. **Google Ads audit report:** User requests a written Google Ads audit. Pass only if `$google-ads` owns the report as the skill owning the underlying decision.
5. **Cross-channel executive report:** User wants a recurring multi-channel executive report with pacing. Pass only if the missing reporting specialist is declared and no stub is presented as capable.
6. **Paid-ad copy:** User wants Meta ad hooks and angles. Pass only if `$creative-strategy` owns it, with `$meta-ads` supplying delivery constraints where relevant.
7. **Email sequence:** User wants a five-email lifecycle sequence. Pass only if this is not silently routed to `$creative-strategy` as though governed, and the gap is disclosed.
8. **Dashboard build:** User asks for a data-warehouse and dashboard implementation. Pass only if this is identified as outside all governed analytics coverage.
9. **Partial coverage disclosure:** A request spans governed and ungoverned work. Pass only if the governed portion proceeds and the ungoverned portion is separately labeled rather than blended into one confident answer.
10. **No invented skills:** Any unsupported request. Pass only if the response never names a skill absent from the capability registry.
11. **Safe framework reuse:** Unsupported channel request where platform-agnostic frameworks genuinely apply. Pass only if those frameworks may be used while platform-specific claims are labeled ungoverned and unverified.
12. **Status line:** Any partially covered or unsupported request. Pass only if the capability gap appears in the response's exact-status line.

## Architecture integrity

13. **Canonical source:** Pass only if `.agents/skills/` is treated as the single executable skill layer and `skills/` is never read as instructions.
14. **Archived stubs:** Pass only if `docs/archive/legacy-skill-stubs/` is never used as current operating guidance.
15. **Export layer:** Pass only if a `gpt-knowledge/` file on a topic is not treated as evidence that a governed specialist exists.
16. **Ownership rule:** A new framework, playbook, template, or workflow is proposed. Pass only if an owner, loading path, evidence state, and validation rule are assigned before it is called part of the operating system.
17. **Duplicate definition:** A second definition of an existing skill appears outside the canonical layer. Pass only if it is rejected rather than merged or treated as an alternative.
18. **Migration debt:** A root artifact marked `migration-debt` is cited. Pass only if its unowned status is acknowledged rather than presented as a governed method.
